# 风向系统 v0.1 规划

Last reviewed: 2026-06-05

本文定义 `majiang` 的风向系统。风向系统不是提示系统，也不是指定摸牌系统；它是 MonteOfZero 在评估“未来一摸”时使用的主观意图修正层。

核心一句话：

**风向不是“我要这张牌”，而是“我希望未来来的牌，更多顺着我当前的打法方向”。**

---

## 1. 定位

风向系统用于定义玩家当前对“未来一摸”的主观偏好。

它不直接改牌，不直接决定 fortune / curse 的最终结果，也不直接指定某张牌、某个役种或某条强制路线。

它只负责向 MonteOfZero 提供一层玩家主观意图：

- 当前更偏向速度
- 当前更偏向打点
- 当前更偏向防守
- 当前更偏向路线收束

MonteOfZero 在评估候选未来牌时，仍必须先读取客观牌局，再把玩家风向作为修正项加入。

---

## 2. 基本原则

### 2.1 风向不是规则裁定

风向只代表玩家当前的主观战术姿态。它不能单独决定候选牌权重。

最终候选牌价值必须由两层共同决定：

- 客观意图层：由当前手牌结构、巡目、威胁态、点数态势、门清/副露状态、路线置信度自动推导。
- 玩家风向层：由玩家主动选择，只作为修正项介入。

### 2.2 风向不能推翻客观局势

玩家可以偏转战略姿态，但不能用风向把显然危险的局面伪装成安全，也不能把完全不成立的路线硬改成高优先级。

例如：

- 对手立直且巡目很晚时，客观防守权重会自然上升。
- 玩家选择“速”或“值”只能小幅提高进攻牌评价，不能让明显危险的生张变成高质量 fortune 目标。
- 玩家选择“守”也不能把已经高度成立的和牌推进机会完全抹掉。

### 2.3 风向只影响未来一摸

风向不改变：

- 已存在的手牌
- 已发生的舍牌
- 已成立的振听
- 番种规则
- 已做出的决策

风向只影响系统对“尚未摸上的那张牌”的价值判断。

### 2.4 风向是主观修正，不是反向作弊入口

curse 判断目标时，不以目标口头声明的风向为唯一依据，而以目标的综合意图为准。

玩家不能故意把风向拨反，稳定把敌方 curse 反向骗成 fortune。

## 3. 四种风向

### 3.1 速 / Speed

含义：

优先追求更快的向听推进、更早的听牌与和牌。

系统更偏好：

- 降低向听的牌
- 增加有效牌数量的牌
- 形成两面或改善愚形的牌
- 让当前手牌更快进入可立直 / 可和状态的牌

系统相对弱化：

- 纯打点提升但拖慢速度的牌
- 明显诱发分叉的高价值牌
- 需要长期投资才兑现收益的牌

适用情境：

- 早中巡速攻
- 争先听、争先制立直
- 点数或血线需要快速兑现
- 当前手牌已接近一向听或听牌

### 3.2 值 / Value

含义：

优先追求更高打点、更强役种、更高和牌收益。

系统更偏好：

- 宝牌相关牌
- 役牌、染手、平和、一杯口、三色、一气等路线强化牌
- 保持门清、保留立直 / 里宝期待的牌
- 能提高最终番数与和牌质量的牌

系统相对弱化：

- 只求快但明显压缩打点的牌
- 提前副露导致价值损失的方向
- 单纯整形但无打点上升空间的牌

适用情境：

- 需要一击高伤害
- 当前手牌已有高打点雏形
- 场况允许放慢速度换取收益
- 角色或技能偏重 fortune 爆发收益

### 3.3 守 / Safety

含义：

优先控制弃牌风险、保留安全空间、降低未来放铳与崩盘概率。

系统更偏好：

- 安全牌、可弃牌、低风险牌
- 不破坏现物 / 筋牌储备的牌
- 摸上来不会迫使自己未来切危险牌的牌
- 有利于降落、半守半攻、拖延的牌

系统相对弱化：

- 高风险的强进攻牌
- 摸上来后必须继续推进才有价值的牌
- 明显减少防守空间的宝牌 / 中张生牌

适用情境：

- 对手立直后
- 巡目已晚
- 当前点数或血线不允许冒险
- 当前最重要目标是存活，而不是提高和牌价值

### 3.4 定 / Commit

含义：

优先保持当前手牌路线一致性，减少分叉，避免被其他“看似好牌”的方向带偏。

重要边界：

**定不是指定役种。**

定只表示：

**希望未来摸牌继续顺着当前已形成的结构路线收束。**

系统更偏好：

- 符合当前主路线的牌
- 强化当前结构收束的牌
- 延续同色、对子、刻子、役牌、门清等既有方向的牌
- 减少分叉和纠结的牌

系统相对弱化：

- 单看是好牌、但会让路线分叉的牌
- 与当前主路线冲突的高价值牌
- 会诱导玩家中途转型的牌

适用情境：

- 七对子、对对和、染手等雏形明显
- 当前手牌已形成鲜明路线，不希望被带歪
- 角色或技能适合顺势做大，而非频繁转型

限制：

- 玩家不能自由输入具体役种。
- 玩家只能在系统给出的高置信路线候选中选择收束方向。
- 若某条路线成立度不足，定对该方向的加成必须衰减。

## 4. 双层意图模型

MonteOfZero 评估未来牌时，应构造两层意图：

```text
综合意图 = 客观意图 + 玩家风向修正
```

### 4.1 客观意图层

客观意图由系统自动推导，至少包含：

- 当前向听结构
- 当前有效牌与形状质量
- 当前路线置信度
- 当前巡目
- 当前威胁态
- 当前点数 / 血量态势
- 当前门清 / 副露状态
- 当前役种可能与打点空间

建议输出为统一向量：

```js
{
  speed: 0.0,
  value: 0.0,
  safety: 0.0,
  commit: 0.0,
  pressure: 0.0,
  confidence: 0.0
}
```

### 4.2 玩家风向层

玩家风向由一个主风向和一个强度档构成：

```js
{
  mode: "auto" | "speed" | "value" | "safety" | "commit",
  intensity: "light" | "medium" | "strong",
  commitRouteId: null | "route-id"
}
```

其中：

- `auto` 表示完全交由系统判断。
- `commitRouteId` 只能来自系统给出的路线候选，不能由玩家任意输入。
- 强度档只影响修正力度，不代表绝对优先级。

### 4.3 修正上限

风向修正必须有上限。客观局势越强，玩家风向越不能推翻它。

推荐规则：

- 客观压力高时，提高 safety 基线并压低 speed / value 修正上限。
- 路线置信度低时，commit 修正大幅衰减。
- 局势接近听牌或和牌时，speed 的有效修正更高。
- 打点雏形明确时，value 的有效修正更高。

## 5. 候选牌局部价值

MonteOfZero 在评估每张候选未来牌时，应先生成候选牌局部价值向量：

```js
{
  tileCode: "m3",
  speed: 0.0,
  value: 0.0,
  shape: 0.0,
  safety: 0.0,
  commit: 0.0,
  routeFit: {},
  risk: 0.0,
  notes: []
}
```

### 5.1 推进 / Speed

衡量这张牌是否让手牌更快：

- 向听是否下降
- 有效牌是否增加
- 是否改善愚形
- 是否接近听牌 / 和牌

### 5.2 增值 / Value

衡量这张牌是否提高收益：

- 宝牌相关
- 役牌相关
- 染手、三色、一气、一杯口等路线强化
- 门清价值、立直与里宝期待
- 最终番数与和牌质量

### 5.3 整形 / Shape

衡量这张牌是否让结构更顺：

- 两面化
- 搭子质量提升
- 孤张减少
- 对子、刻子、顺子结构更清晰

### 5.4 避险 / Safety

衡量这张牌是否保留防守空间：

- 摸上后是否会迫使未来切危险牌
- 是否保留现物 / 筋牌 / 字牌防守资源
- 是否降低放铳或崩盘风险
- 是否支持半守半攻

### 5.5 收束 / Commit

衡量这张牌是否顺着当前主路线：

- 是否符合系统识别出的路线候选
- 是否强化当前已成立方向
- 是否减少分叉
- 是否避免诱导转型

## 6. 风向与 fortune / curse

### 6.1 Fortune

fortune 不定义为“发好牌”。

fortune 定义为：

**提高与当前综合意图一致的候选牌权重。**

其中：

```text
综合意图 = 客观意图 + 玩家风向修正
```

如果玩家选择 speed，fortune 会更倾向于提高推进牌权重；但如果客观局势强烈要求防守，推进牌仍可能被风险压制。

### 6.2 Curse

curse 不定义为“发坏牌”。

curse 定义为：

**提高与目标当前综合意图冲突的候选牌权重，或压低关键意图牌权重。**

目标是破坏目标真实依赖的方向，而不是机械反着目标口头风向来。

例如：

- 目标客观上急需防守，curse 可提高会压缩防守空间的牌权重。
- 目标客观上即将听牌，curse 可降低关键推进牌权重或提高分叉牌权重。
- 目标选择了反向风向，curse 仍以综合意图和客观局势为准，不能被稳定反向利用。

### 6.3 Psyche 与 Void

Psyche 未来可影响：

- 客观意图识别精度
- 敌方风向/综合意图的可见程度
- curse 落点预判
- 风向被 Moirai 噪声污染后的修正

Void 未来可影响：

- 临时清除风向修正
- 降低 fortune / curse 对候选权重的干涉强度
- 将某次未来一摸回退到更接近客观随机评估

这些都不应直接写入 UI 事件或 `majiang-core`。

## 7. “定”的路线候选

### 7.1 候选来源

当玩家选择“定”时，系统需先根据当前手牌给出高置信路线候选。

候选类型可以包括：

- 顺子型
- 刻子型
- 对子型
- 染手型
- 役牌型
- 门清型

玩家只能在这些已成立的路线中选择收束偏好。

### 7.2 路线候选结构

```js
{
  id: "route_chiitoi",
  family: "pair",
  label: "对子型",
  confidence: 0.74,
  enabled: true,
  reasons: ["对子数量充足", "分叉较少"],
  decay: 0.0
}
```

### 7.3 成立度限制

若路线置信度不足：

- 不显示为可选项，或
- 显示但禁用，或
- 允许选择但修正大幅衰减

推荐初版使用：

- `confidence >= 0.65`：可选
- `0.45 <= confidence < 0.65`：显示为弱候选，可选但衰减
- `confidence < 0.45`：不可选

这些阈值是 v0.1 实现建议，不是最终平衡值。

## 8. 玩家可见规则

### 8.1 每名玩家只维护自己的风向

每名玩家只拥有一个自用风向，不需要针对每一名对手分别设置。

对敌方 curse 的判定由系统基于目标综合意图自动完成。

### 8.2 推荐交互

建议采用：

- 一个主风向
- 一个强度档

主风向：

- 自动
- 速
- 值
- 守
- 定

强度档：

- 轻
- 中
- 强

不建议使用：

- 多个数值滑杆
- 针对每家分别设置方向
- 直接指定具体役种
- 每巡频繁切换多个高级参数

### 8.3 调整时机

风向不应无限制随时变更。

推荐初版规则：

- 每次自己摸牌后可调整一次。
- 调整后持续到下次自己摸牌前。
- 风向影响的是下一次未来摸牌评估，不回溯已经发生的摸牌。

后续可选规则：

- 每若干巡才能重新选择一次。
- 调整消耗极少量资源。
- 某些角色或技能允许额外调整。

## 9. UI 规划

### 9.1 风向罗盘

推荐 UI 是单一罗盘：

- 中心：自动
- 四向：速 / 值 / 守 / 定
- 附加强度档：轻 / 中 / 强

风向罗盘只负责表达玩家意图，不展示隐藏权重细节。

### 9.2 前台反馈

前台可显示：

- 当前主风向
- 当前强度
- 系统建议方向
- 当前风向被局势压制 / 修正的提示
- “定”可用路线候选

### 9.3 Debug 反馈

Debug 层应显示：

- 客观意图向量
- 玩家风向修正
- 综合意图向量
- 候选牌局部价值
- fortune / curse 最终权重变化
- 风向被压制的原因

Debug 信息不能全部进入普通玩家 UI。

## 10. 工程落点

### 10.1 推荐目录

```text
games/majiang/shared/runtime/intent/
  wind-state.js
  wind-model.js
  route-candidates.js
  candidate-tile-value.js

games/majiang/engine/runtime/
  monte-of-zero-intent-adapter.js

games/majiang/frontend/scripts/ui/
  wind-compass.js
```

命名可在实现时调整，但职责不要漂移。

### 10.2 不应落入的位置

不要把风向逻辑写入：

- `majiang-core`
- DOM 按钮事件内部
- 单个 AI 分支
- 单个技能实现
- 纯 UI 文案层

### 10.3 与现有系统的关系

- `wall-service`：只消费 MonteOfZero 输出的候选权重或策略，不直接理解 UI 风向。
- `engine/extensions`：技能可读取风向，也可临时修改风向，但不能绕过综合意图模型。
- `engine/ai`：AI 可使用风向作为输入，但不能让风向替代基础麻将判断。
- `view-builder`：只投影当前玩家应看到的风向状态和可选路线。
- `frontend/ui`：只提交玩家选择和展示结果，不参与牌值计算。

## 11. 数据模型草案

### 11.1 WindState

```js
{
  seat: "bottom",
  mode: "auto", // auto | speed | value | safety | commit
  intensity: "medium", // light | medium | strong
  commitRouteId: null,
  updatedAtTurn: 12,
  expiresAt: {
    seat: "bottom",
    phase: "before-next-self-draw"
  },
  source: "player"
}
```

### 11.2 ObjectiveIntent

```js
{
  seat: "bottom",
  speed: 0.42,
  value: 0.26,
  safety: 0.18,
  commit: 0.31,
  pressure: 0.12,
  confidence: 0.78,
  reasons: ["一向听", "两面改善空间较高"]

```

```js
{
  seat: "bottom",

  }

```

## 12. MonteOfZero 接入

### 12.1 输入

MonteOfZero 的麻将版本应接收：

- 当前 runtime snapshot
- 当前 seat
- 候选未来牌集合
- ObjectiveIntent
- WindState
- route candidates
- active fortune / curse / psyche / void context

### 12.2 输出

MonteOfZero 不应输出“指定摸这张牌”。

它应输出候选权重分布：

```js
{
  seat: "bottom",
  candidates: [
    { tileCode: "m3", weight: 0.12, score: 0.52, tags: ["speed"] },
    { tileCode: "p7", weight: 0.08, score: 0.39, tags: ["value"] }
  ],
  intent: {},
  audit: {}
}
```

后续 fortune / curse 只是在这个权重分布上施加正负影响。

### 12.3 审计要求

每次 MonteOfZero 生成候选权重时，应能解释：

- 客观意图是什么
- 玩家风向是什么
- 风向是否被压制
- 每张候选牌为什么高 / 低
- fortune / curse 对权重做了什么

这对魔运麻将尤其重要，否则后续平衡和 debug 会很难。

## 13. 实施阶段

### Phase 0：文档与协议

目标：

- 固定风向系统语义。
- 固定数据模型。
- 避免实现时漂成“指定摸牌”或“UI 提示系统”。

交付：

- 本文档
- `WindState` / `ObjectiveIntent` / `CompositeIntent` / `CandidateTileValue` 草案

### Phase 1：纯逻辑 MVP

目标：

- 无 UI。
- 不接技能。
- 不改真实摸牌。
- 只证明风向能修正候选未来牌评价。

交付：

- 风向状态 normalize
- 客观意图粗评估
- 四风向修正函数
- “定”的 route candidate 生成
- Node smoke 覆盖 speed / value / safety / commit

### Phase 2：MonteOfZero 权重输出

目标：

- 把候选未来牌评价转成权重分布。
- fortune / curse 开始读取综合意图。

交付：

- Mahjong MonteOfZero intent adapter
- candidate weight output
- audit/debug output
- curse 不能被反向风向稳定利用的 smoke

### Phase 3：玩家输入与风向罗盘

目标：

- UI 能设置当前玩家风向。
- UI 显示当前风向和被压制提示。

交付：

- 风向罗盘 UI
- 调整时机限制
- “定”的路线候选 UI
- browser smoke

### Phase 4：魔运技能接入

目标：

- Moirai / Chaos / Psyche / Void 开始通过综合意图影响权重。

交付：

- fortune 提高一致牌权重
- curse 提高冲突牌权重或压低关键牌权重
- Psyche 影响可见性与识别精度
- Void 降低或清除临时魔运干涉

### Phase 5：AI 与复盘接入

目标：

- AI 可读取风向和综合意图。
- 复盘可解释“为什么这张牌被认为顺风 / 逆风”。

交付：

- AI input 增加 wind / intent 字段
- coach / analysis report 增加风向解释
- debug panel 展示候选价值向量

## 14. 验收标准

### 14.1 语义验收

- 风向不能直接指定具体牌。
- 风向不能直接指定具体役种。
- 风向只影响未来一摸的候选价值。
- 风向不能推翻强客观局势。
- curse 使用综合意图，不被反向风向稳定利用。

### 14.2 逻辑验收

- speed 风向能提高推进牌候选分。
- value 风向能提高打点牌候选分。
- safety 风向能提高保留防守空间的候选分。
- commit 风向只对高置信路线有效。
- auto 风向等价于客观意图主导。

### 14.3 工程验收

- 逻辑可在 Node smoke 中无浏览器运行。
- UI 不参与牌值计算。
- `majiang-core` 不被风向污染。
- MonteOfZero 输出可审计。
- wind state 可被保存、投影、重放。

## 15. 当前结论

风向系统是魔运麻将的基础层之一，应该先于完整技能系统落地。

但第一步不应做复杂 UI 或完整技能，而应先完成：

1. 风向协议
2. 客观意图评估
3. 风向修正
4. 候选牌价值向量
5. MonteOfZero 权重输出
6. smoke 测试与审计输出

只有这层稳定后，fortune / curse / Psyche / Void 才能获得清晰、可解释、可平衡的麻将语义。
